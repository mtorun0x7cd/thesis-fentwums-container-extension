### E-001

- **Location:** p. 1 (PDF p. 16), Section 1.1
- **Quoted text:** "Users are currently required to manually install and configure complex binaries that vary significantly between operating systems"
- **Correction:** OneWare Studio already has a package manager that downloads toolchain binaries such as GHDL and the OSS CAD Suite in the build for the host's operating system, installs them and fills in their path settings. The tools installed that way still run natively on the host, so the problem the thesis addresses, native toolchains that differ between hosts and operating systems, remains; but the statement that users must install and configure these binaries manually overstates it.
- **Class:** factual, not affecting results
- **Evidence:** OneWare Studio source code (github.com/one-ware/OneWare, commit a3a5a79 of 2026-06-25): the module OneWare.OssCadSuiteIntegration defines the OSS CAD Suite as a package of the category Binaries with downloads for Windows, Linux and macOS, and the package manager's installer for such packages fills in the tool's path setting on installation. GHDL extension for OneWare Studio (github.com/one-ware/OneWare.GhdlExtension, commit 01d1406 of 2026-03-26): GHDL is defined in the same way. README of the FEntwumS NetlistViewer extension (github.com/FEntwumS/FEntwumS.NetlistViewer, commit 2ef4d51 of 2026-06-26), sections Dependencies and Installation: GHDL and the OSS CAD Suite are listed as binaries that are available in the package manager.
- **Found:** 2026-09-27
- **Reported:** not reported
- **Status:** confirmed

### E-005

- **Location:** p. 14 (PDF p. 29), Section 2.3.2; p. 66 (PDF p. 81), Section 6.5.4
- **Quoted text:** p. 14: "In runtime environments like RunD [18], directory-sharing mechanisms are bypassed in favor of a block-level device overlay (virtio-blk) configured via device-mapper." and "accommodating up to 2500 concurrent instances on a single physical host node"; p. 66: "In high-density serverless container platforms (e.g., RunD [18]), directory sharing protocols are completely bypassed." and "containers read and write their active filesystems to virtualized raw block devices (virtio-blk) managed via host-level device mappers"
- **Correction:** RunD [18] does not bypass directory sharing. It splits the container root file system: the read-only layer is shared from the host through virtio-fs, and a volatile writable layer is provided through virtio-blk, backed by a storage image on the host; the guest combines the two with overlayfs. [18] treats block devices prepared with device-mapper as the conventional approach, which could not meet its concurrency requirement, not as its own design. [18] reports that over 2,500 secure containers can be deployed on a node with 384 GB of memory; "up to 2500" inverts the bound. [18] presents its startup and density figures as results of its whole design, which besides the root file system also covers the guest kernel and the host's cgroups, not as results of virtio-blk with page cache sharing alone, as p. 14 puts it.
- **Class:** attribution
- **Evidence:** [18], full text (USENIX ATC '22, pp. 53-68): abstract, Section 3.1, Section 4.1 (design overview) and Section 4.2.
- **Found:** 2026-09-24
- **Reported:** not reported
- **Status:** confirmed

### E-009

- **Location:** p. 22 (PDF p. 37), Section 3.2.2; p. 23 (PDF p. 38), Section 3.3; p. 24 (PDF p. 39), Table 3.1, column Functional Package Managers, rows Virtualization Boundary and Security Isolation Boundary
- **Quoted text:** p. 22: "Because FPMs operate exclusively at the filesystem level, they lack runtime namespace containment. Processes execute directly on the host, sharing the host’s PID tree, network devices, and user directories, which poses substantial security risks when building untrusted EDA scripts."; p. 23: "but their lack of runtime network and process namespace containment leaves the host exposed to untrusted build scripts"; p. 24, Table 3.1: "Filesystem-level (Cryptographic hash-based store paths; absolutely no kernel namespace isolation)." and "Unprivileged native space (Relies entirely on standard POSIX user permissions)."
- **Correction:** Builds are isolated on Linux. Nix runs each build in a sandbox with private PID, mount, network, IPC and UTS namespaces, which is on by default on Linux (fixed-output derivations keep network access); the Guix build daemon runs builds in an isolated chroot environment with a separate PID namespace. Outside a build, GNU Guix can also run programs in an isolated container (guix shell --container), which by default has no network access and shares no files with the host other than the current working directory. The statements hold for programs run from a Nix development shell or from a Guix shell without that option, and for Nix builds on platforms other than Linux, where the sandbox is off by default. They do not hold for Nix or Guix builds on Linux, nor for programs run in a Guix container.
- **Class:** factual, not affecting results
- **Evidence:** Nix Reference Manual 2.35.2, configuration option sandbox; GNU Guix Reference Manual 1.5.0, sections Build Environment Setup and Invoking guix shell (options --container and --network).

### E-013

- **Location:** p. 42 (PDF p. 57), Section 5.4.2, Listing 5.3
- **Quoted text:** "so that the matcher is generated at compile time rather than built at runtime"; Listing 5.3: "RegexOptions.ExplicitCapture | RegexOptions.IgnoreCase | RegexOptions.NonBacktracking,"; "By using the [GeneratedRegex] attribute, the C# compiler emits specialized matcher code in Intermediate Language (IL) during the build.
